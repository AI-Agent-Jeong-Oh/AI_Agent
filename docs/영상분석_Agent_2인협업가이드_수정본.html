02 · 공동 작업 공간

GitHub는 팀의 기준, VS Code는 실행하는 곳

개발용 LLM과 앱 안에서 영상을 분석하는 AI는 역할이 다릅니다. 개발용 LLM 사용 여부가 앱의 로컬 / 외부 API 모드를 결정하지 않습니다.

공간 / 도구사용 방식
GitHub Organization팀 소유 공간. 무료 Organization + Private 저장소 1개로 시작하는 제안
video-analysis-agent 저장소소스·공통 요구사항·프롬프트 규칙·워크플로우·변경 이력 관리
Issues / ProjectsIssue별 담당자·완료 조건·수정 파일 범위 지정. 할 일 → 진행 → 리뷰 → 완료
VS Code + Git각자 저장소를 Clone하고 브랜치에서 개발·실행·변경 비교·Commit·Push
개발용 LLM / 코딩 도구현재 코드와 요구사항을 읽게 하고 작은 작업 단위로 코드·테스트·오류 수정 요청
PC 데이터 폴더선택한 영상 묶음, 실제 영상 경로, 생성 클립·프레임·결과 보관

03 · LLM과 개발

사람이 방향을 정하고, LLM이 구현을 돕습니다

한 번에 전체 앱을 생성시키기보다 기능 하나씩 연결합니다. LLM이 “완료”라고 말해도 실제 실행 결과로 완료 여부를 판단합니다.

1

Issue 선택

담당자와 완료 조건을 확인합니다. 예: “영상 경로를 선택하면 파일명·길이가 표시된다”.

2

최신 main에서 브랜치 생성

작업 중 변경을 먼저 정리하고 최신 코드를 받습니다. 예: feature/video-picker.

3

LLM에 작업 요청

공통 규칙, 현재 코드, 이번 범위, 완료 조건을 전달합니다. 먼저 수정 계획과 대상 파일을 확인합니다.

4

코드 적용·실행·오류 수정

LLM이 만든 변경을 확인하고 PC에서 실행합니다. 오류 메시지와 재현 순서를 다시 전달해 수정합니다.

5

검토 후 Commit·Push

의도한 파일만 Stage합니다. 영상·API 키·개인 경로가 들어가지 않았는지 diff를 확인합니다.

6

PR 리뷰·병합

다른 팀원이 변경 코드와 실행 결과를 검토합니다. 수정은 같은 브랜치에서 반영합니다.

7

팀원 모두 최신화

병합 후 main을 Pull합니다. LLM의 다음 작업도 갱신된 코드와 문서를 기준으로 시작합니다.

작업 시작

git status
git switch main
git pull --ff-only
git switch -c feature/video-picker

작업 공유

git diff
# VS Code에서 의도한 파일만 Stage
git diff --cached
git commit -m "Add local video picker"
git push -u origin feature/video-picker

파일 저장은 내 PC에만 반영됩니다. Commit은 로컬 이력, Push는 원격 브랜치 공유, PR 병합은 공용 main 반영입니다. VS Code의 Source Control에서 같은 작업을 수행할 수 있습니다.

04 · 2인 분담

승재는 구조·핵심 연동, 누나는 화면·데이터·검색

복잡도가 높은 전체 설계와 Agent 연결은 승재님이 맡고, 누나도 UI와 자료 검색을 독립적으로 구현합니다. 문서·테스트만 맡기는 분담이 아닙니다.

05 · 데이터와 공통 PDF

시연 영상, 평가 라벨, 참고 문서를 분리합니다

공식 설명은 MP4 영상과 JSON 라벨, normal·symptom·action 구간 및 시작·종료 시각을 안내합니다. VS9/VL9의 실제 파일 대응과 포함 유형은 압축 해제 후 확인합니다.

자료보관·사용 방식공유 기준
선택 영상 묶음각 PC의 local_data/ 또는 설정한 데이터 폴더. 실행 중 파일 경로 참조Git에 영상 업로드 대신 데이터셋·파일 키·설정 방법 공유
VL9의 JSON 라벨이벤트와 시간 정보 등은 결과를 대조하는 용도로 별도 보관모델의 독립 분석을 확인할 때 정답 JSON·정답 분류 경로를 입력에 주지 않음
공통 PDF 변환 자료resources/knowledge/ 등 앱의 읽기 전용 리소스에 포함배포 가능한 자료 범위 확인. 변환 코드·버전 목록은 Git으로 관리
분석 결과·프레임·클립쓰기 가능한 사용자 데이터 폴더에 저장실제 결과와 로그는 소스 저장소에서 제외
모델·API 키모델은 별도 설치 경로, 키는 로컬 설정가중치·키는 Git에 넣지 않음
동일한 파일을 사용한다는 것은 각 PC의 경로도 같아야 한다는 뜻이 아닙니다. 데이터셋 번호 515, VS9 키 53067·VL9 키 53047, 원래 파일명과 파일 체크섬을 공통 목록으로 관리하고 PC별 경로는 로컬 설정으로 지정합니다.

다운로드 후 누나가 먼저 확인할 것

  1. VS9와 VL9를 다른 폴더에 해제하고 JSON의 filename으로 영상을 매칭합니다.
  2. 실제 영상 수·길이·해상도와 재생 실패를 목록화합니다.
  3. 라벨의 유형과 시간 필드를 확인하고 변환 규칙을 기록합니다. 파일명 숫자 9를 행동 유형 번호로 단정하지 않습니다.
  4. 개발용과 최종 확인용 영상을 구분합니다. 같은 장면의 다른 카메라 영상이 있으면 함께 묶어 분리합니다.
  5. 모델 입력에는 라벨 정답과 분류명을 숨기고, 누나의 검토 도구에서만 결과와 대조합니다.

공통 PDF 준비와 업데이트 · 누나 구현 / 승재 연결

1

배포 전 변환

자료 담당자가 PDF를 확정하고 텍스트 추출·필요 시 OCR·분할·페이지 대조를 수행합니다.

2

검색 데이터 생성

본문·출처·페이지·기준일·색인·자료 버전을 묶습니다. 벡터 검색은 색인과 질문에 같은 임베딩 모델·버전·차원을 사용합니다.

3

프로그램에 포함

사용자가 PDF를 저장·등록하지 않아도 검색할 수 있게 패키징합니다. 두 AI 모드가 같은 로컬 검색기와 내장 자료를 사용합니다.

4

자료가 바뀔 때 갱신

자료나 임베딩 모델이 바뀌면 다시 변환·색인·검증합니다. 새 패키지를 배포하고 결과에 사용한 자료 버전을 기록합니다.

외부 API 모드에서는 검색된 근거 발췌를 답변 생성에 전달합니다. 로컬 모드는 같은 근거를 PC에서 해석합니다. 관련 자료가 없으면 미확인으로 표시하고 법 관련 적용 여부는 사람이 검토합니다.

07 · 검토와 설치 배포

실제로 동작한 결과로 PR을 검토합니다

LLM이 작성한 코드도 팀원이 이해할 수 있는 변경 단위로 나누고, 해당 기능에 맞는 실행 결과를 남깁니다.

PR에 남길 내용

관련 Issue: #번호
변경 이유와 사용자 동작:

실행한 환경: OS / Python / AI 모드 / 모델 버전

설치형 배포 순서

  1. 지원 OS를 확정합니다. 첫 버전은 팀의 주 사용 OS 하나부터 완성합니다.
  2. 실행 파일 묶음을 만듭니다. PyInstaller는 빌드 대상 OS에서 실행합니다. 초기에는 one-folder 방식으로 누락 파일을 확인합니다.
  3. 공통 PDF 데이터와 필요한 구성 요소를 포함합니다. FFmpeg, 검색 자료, 설정 기본값의 포함 여부를 확인합니다. 대용량 모델은 별도 패키지로 준비할 수 있습니다.
  4. 설치 패키지를 만듭니다. PyInstaller 결과물과 설치 마법사는 별개입니다. 필요하면 OS별 설치 도구를 추가합니다.
  5. 새 PC에서 확인합니다. 개발용 Python·VS Code 없이 앱을 실행하고, 선택 영상 경로·모델 설정·내장 PDF 검색·결과 재생을 확인합니다.
  6. 버전과 사용법을 배포합니다. 코드·앱·모델·자료 버전을 기록합니다. GitHub 자동 Source code.zip 대신 실제 배포 파일을 구분해 제공합니다.
시연 영상은 공통 PDF와 달리 앱에 자동으로 묶지 않습니다. 이번 개발은 PC에 준비한 선택 영상 경로를 읽는 구조입니다. 사용자는 앱 설치 후 분석할 영상 위치를 지정합니다.

시간 절감 평가

같은 영상과 요구사항에 대해 수작업 탐색 시간과 Agent 결과를 보고 원본을 확인한 시간을 비교합니다. AI 처리 대기 시간과 전체 완료 시간은 따로 기록합니다. 반복 시청으로 익숙해지는 영향을 줄이도록 비교 순서·참여자·동등한 영상 사용 방식을 정하세요.

JSON이 있으면 보조적인 구간 대조에 활용할 수 있습니다. 현재 핵심 평가는 영상 확인 시간이며, 소수 영상의 결과를 전체 유형에 대한 정확도로 제시하지 않습니다.
